# RFC 014: a two-tier tile cache

Fernway Maps serves raster and vector tiles to about four hundred small customers: hiking clubs,
ferry operators, two regional newspapers and one very demanding orienteering federation. This RFC
proposes replacing the single Redis cache in front of the renderer with a two-tier cache, so that a
cold zoom level no longer takes the whole render fleet with it.

**Decision wanted by:** the end of the spring planning cycle. **Owner:** Rowan Vale.

## Summary

We keep a small in-process cache on every edge node and add a shared object-store tier behind it.
A tile request checks memory first, then the object store, and only then the renderer. The renderer
writes through both tiers. Invalidation moves from "flush everything on a style change" to a
versioned key, so publishing a style is cheap and rolling one back is instant.

Nothing changes for customers except latency: the tile URLs, the API keys and the attribution rules
all stay as they are in the [API reference](api-reference.md#tiles).

## Motivation

The current cache was fine when we had one style and thirty customers. Today a single flush makes
every edge node miss at once, the renderer queue climbs past its limit within a minute, and the
on-call engineer spends the next hour watching graphs and apologising to the ferry operators.

Three incidents this winter had the same shape. In each of them clients receive stale tiles for
several minutes after the flush, because the retry path serves whatever the last good response was,
and then the queue drains in bursts that look like a second outage.

| Incident | Date | Trigger | Peak queue | Customer-visible minutes |
|---|---|---|---:|---:|
| INC-211 | 11 December | style publish, `outdoor-v7` | 18,400 | 42 |
| INC-219 | 9 January | Redis failover in `eu-north` | 26,100 | 67 |
| INC-221 | 20 January | expired certificate on the poller | 12,900 | 18 |
| INC-224 | 2 February | bulk re-render of contours | 31,750 | 95 |

Spending tells a similar story. Our Redis cluster keeps 380 GB resident, largely single-use tiles,
at a rate per gigabyte no other line on our bill comes close to. Object storage costs one twentieth
as much, and already holds every rendered archive.

### What we measured

We sampled a week of edge logs in January, about 2.1 billion requests across all customers. The
shape is what every tile server sees: a small hot set and a very long tail.[^sampling]

| Zoom band | Share of requests | Share of distinct tiles | Hit rate today |
|---|---:|---:|---:|
| z0 to z6 | 21.4% | 0.1% | 99.7% |
| z7 to z10 | 38.9% | 2.6% | 96.2% |
| z11 to z13 | 27.3% | 18.4% | 81.5% |
| z14 to z16 | 11.0% | 49.7% | 44.0% |
| z17 and above | 1.4% | 29.2% | 12.3% |

A memory tier of 8 GB per node would have served 71% of those requests by itself. Almost everything
in the z14 to z16 band is cheaper to fetch from an object store than to keep in memory, even at a
p99 of 40 ms.

### Goals

1. A style publish causes no renderer load beyond the tiles people actually ask for.
2. Losing any one cache tier degrades latency, not availability.
3. Monthly cache spend drops by at least a third.
4. An on-call engineer can explain the state of a tile with one command.

### Non-goals

- Changing the tile URL scheme, or anything else a customer has hard-coded into an app.
- Multi-region write consistency. A tile may differ between regions for a few minutes.
- Caching the geocoder. It has its own problems and its own RFC.

## Design

### Request path

Each edge node runs the tile service, which owns the memory tier. The object-store tier is one
bucket per region. The flow for a request is deliberately boring:

```text
client ──► edge node
             │ 1. memory tier (per node, LRU, 8 GB)
             │ 2. object store (per region, 30-day lifecycle)
             │ 3. single-flight guard ──► render queue ──► renderer
             ▼
           response + write-through to 2 and 1
```

The single-flight guard is the piece that was missing in every incident above. When two hundred
clients ask for the same missing tile, one render happens and the other requests wait for it, up to
a deadline of 800 ms, after which they get the previous version of the tile if there is one.

### Key format

A tile's cache key names everything that can change its bytes, in the order that makes listing a
prefix useful:

```text
t/{style_id}/{style_rev}/{dataset_rev}/{z}/{x}/{y}.{fmt}
```

`style_rev` is a counter bumped on each publish and `dataset_rev` is the date of the data build, so
a publish never overwrites anything. The active revision of each style lives in one small table
that edge nodes poll every five seconds:

```sql
CREATE TABLE active_style (
    style_id    TEXT PRIMARY KEY,
    style_rev   INTEGER NOT NULL,
    dataset_rev TEXT NOT NULL,
    published_at TIMESTAMP NOT NULL DEFAULT now(),
    published_by TEXT NOT NULL
);

-- Rolling back is one update; the old tiles are still in the bucket.
UPDATE active_style SET style_rev = style_rev - 1 WHERE style_id = 'outdoor';
```

### The memory tier

Each node holds an LRU keyed by the string above with a byte budget rather than an entry budget,
because a z3 vector tile can be three hundred times the size of a z16 raster one. The eviction loop
lives in the tile service and is small enough to read in one sitting:

```rust
pub struct MemoryTier {
    entries: LruCache<TileKey, Bytes>,
    used: usize,
    budget: usize,
}

impl MemoryTier {
    pub fn insert(&mut self, key: TileKey, tile: Bytes) {
        self.used += tile.len();
        if let Some(old) = self.entries.put(key, tile) {
            self.used -= old.len();
        }
        while self.used > self.budget {
            let Some((_, evicted)) = self.entries.pop_lru() else { break };
            self.used -= evicted.len();
        }
    }
}
```

Tiles above 512 KB never enter this tier. They are rare, mostly dense city centres at z13 in the
vector styles, and a handful of them could otherwise push out thousands of small tiles.

### The object-store tier

One bucket per region, with a lifecycle rule that expires objects 30 days after their last write.
Reads carry a 150 ms timeout: past that we treat it as a miss and render, because the renderer's
median is lower than a slow object store's tail.

```yaml
# deploy/regions/eu-north.yaml
tile_cache:
  bucket: fernway-tiles-eu-north
  lifecycle_days: 30
  read_timeout_ms: 150
  write_concurrency: 64
  memory_budget_gb: 8
  max_memory_tile_kb: 512
```

Writes happen after the response is sent, on a bounded queue. If the queue is full the write is
dropped and counted. A dropped write costs one extra render later, which is the right trade during
an incident.

### Capacity planning

The memory tier's budget comes from the zoom-band table rather than from a guess. At 8 GB a node
holds about 410,000 average tiles, which covers the z0 to z10 band outright and the busiest part of
z11 to z13. A larger budget buys little: doubling to 16 GB would have raised the hit rate in the
January sample from 71% to 74%, at a cost of about $1,850 a month, which no one could justify.

The object store's size follows from the lifecycle rule. Each region keeps what was written in the
last 30 days, and the replay suggests that is about 18 TB in `eu-north` and much less elsewhere:

| Region | Distinct tiles a month | Average size | Stored |
|---|---:|---:|---:|
| `eu-north` | 410 million | 44 KB | 18.0 TB |
| `eu-west` | 290 million | 41 KB | 11.9 TB |
| `eu-south` | 180 million | 39 KB | 7.0 TB |
| `me-south` | 60 million | 36 KB | 2.2 TB |
| `il-central` | 40 million | 38 KB | 1.5 TB |
| `ap-northeast` | 150 million | 52 KB | 7.8 TB |

These numbers change slowly, because a new customer mostly reads tiles somebody else already has.
The exception is a new region of the world, which starts cold. When a customer in a new area signs,
the warm job runs for that area first, and the sales conversation should include a week's notice.

### Consistency between tiers

A tile's key contains its revisions, so two tiers can never disagree about the bytes of a given key.
They can only disagree about whether they have it, and either answer is safe. This is the property
that makes the design simple, and it is worth protecting: anything that would write different bytes
under an existing key, such as a "quick fix" to one tile, is forbidden by the write path, which
refuses to overwrite an object that exists and has a different hash.

The one window worth describing is during a publish. For up to five seconds, nodes differ on which
revision is active, and a user panning across a boundary between nodes could in theory see two
styles side by side. In practice a client talks to one node for the length of a connection, and in
the replay this affected fewer than one request in a million. We accept that.

### Failure modes

| Failure | What happens | What the customer sees |
|---|---|---|
| Memory tier lost (node restart) | Node warms from the object store | p95 rises for about two minutes on that node |
| Object store slow | Reads time out at 150 ms, renders rise | Slightly slower tiles, no errors |
| Object store down | Writes dropped, reads skipped, single-flight holds | Slower tiles; the render queue may shed z17+ |
| Render queue over limit | Previous-revision tile served, else 503 with `Retry-After` | Stale style for a few minutes at worst |
| Poll of `active_style` fails | Node keeps the last revision it knew | A publish reaches that node late |

The last row is the one people ask about. A node that cannot read the table keeps serving the
revision it has, and it raises an alert after sixty seconds. Serving yesterday's style is a much
better failure than serving nothing.

## Rollout

We ship this behind a per-customer flag and move customers in the order that hurts least if it goes
wrong:

1. Internal styles and the demo site, for one week.
2. The walking and hiking clubs, who mostly read at weekends and tell us about problems politely.
3. The newspapers, whose traffic is spiky and a good test of the single-flight guard.
4. Ferry operators and the orienteering federation, once the graphs have been boring for a fortnight.

Each step has the same exit check: p95 no worse than the control group, no increase in 5xx, and
renderer load flat or falling. We are confident the first step can begin about three weeks after
this RFC is accepted, and that the whole rollout fits within one quarter.

### Migration of existing data

Nothing is migrated. The first request for each tile misses, renders once and fills the new tiers,
and Redis stays up in read-through mode for two weeks so that a rollback costs nothing. To avoid a
cold start, a small job replays the top 200,000 tile coordinates from last week's logs before each
customer moves.

```python
# tools/warm_top_tiles.py
def warm(customer, top_n=200_000, rate_per_second=400):
    """Replay the most requested tiles so a moved customer starts warm."""
    for tile in top_tiles(customer, days=7, limit=top_n):
        request_tile(customer, tile, headers={"X-Fernway-Warm": "1"})
        throttle(rate_per_second)
```

### Monitoring

New metrics, all per region and per tier:

- `tile_cache_requests_total{tier,result}`, where `result` is one of `hit`, `miss` and `timeout`
- `tile_cache_bytes{tier}`, against the memory budget
- `tile_singleflight_waiters`, a gauge, the first thing to look at in an incident
- `tile_cache_dropped_writes_total`, which should be near zero outside incidents

The on-call dashboard gets one new row, and `fernway-tiles explain z/x/y --style outdoor` prints
which tier holds a tile, under which revision and how old it is.

### Cache invalidation

Old revisions are never deleted by hand. A publish bumps `style_rev`, nodes pick it up within five
seconds, and tiles under the old prefix simply stop being requested and age out. For the rare case
of a legal takedown, such as a private road a court has told us to remove, there is a targeted
command that lists the affected tile coordinates and deletes them from every revision:

```bash
fernway-tiles purge --bbox 11.92,57.68,11.97,57.71 --zoom 12-18 --reason "takedown 2041"
```

The command writes an audit line with the reason, and it refuses to run without one. Purging a
bounding box above a few square kilometres needs a second person, which is enforced by the tool
asking for their approval token rather than by anyone remembering the rule.

## Alternatives rejected

### Option A: a bigger Redis

The cheapest thing to try, and we did try it in 2024. Doubling the cluster moved the failure out by
about four months of growth. It does nothing for the flush problem, and memory is the thing we most
want to buy less of.

### Option B: a third-party CDN in front of everything

A CDN would absorb the hot set well, and we may still add one for the static assets. It does not
remove the need for an origin cache, because the long tail is where we hurt, and CDN hit rates at
z14 and above are poor for the same reason ours are. It would also put a fourth party between
customers and their tiles, and two of the ferry operators have contracts that name our subprocessors.

### Option C: pre-render everything

The orienteering federation asks for this about once a year. Rendering every tile to z16 for one
style takes around nine days on the current fleet and produces about 48 TB, most of which nobody
will ever look at. It makes style publishes take a week rather than a minute, which rules it out
regardless of the cost.

Pre-rendering a small set remains sensible, and the warm job in the rollout is exactly that.

## Security and privacy

Tiles hold no customer data, but the logs we use to pick the warm set hold request coordinates, and
a hiking club's logs can say a fair amount about where a small group of people walk. The warm job
reads only aggregated counts per tile, never raw request lines, and the counts are dropped below a
threshold of ten requests a week.

Bucket access uses the node's existing workload identity. No new credentials are created, and no
customer API key ever reaches the cache layer.[^keys]

## Testing

- **Unit:** eviction accounting, key parsing, the single-flight guard's deadline behaviour.
- **Replay:** one week of sampled logs against a staging region, comparing hit rates per zoom band
  with the table above.
- **Failure drills:** block the object store, kill the poller, restart half a region's nodes. Each
  drill has a written expected result and somebody watching.
- **Load:** 2× the January peak for one hour, with a style publish in the middle of it.

The publish-under-load test is the one that matters. If it passes, the incidents above could not
have happened the way they did.

## Open questions

1. Should the render deadline differ per customer? The orienteering federation would accept a slow
   tile over a stale one, and everybody else would not.
2. Does a vector tile's size budget need to be separate from a raster one's? The eviction loop
   treats bytes as bytes, and that may be too simple.
3. Who owns the warm job after the rollout: the tile team, or whoever runs data builds?
4. Should a customer be able to see which tier served a tile? An `X-Fernway-Cache` header would be
   very cheap to add, and support would love it.

## Appendix: what happened in INC-224

Written up here because it is the incident people quote, and the short version gets it wrong.

At 02:10 on 2 February the nightly contour build finished with a new elevation source, which changed
about 11% of all tiles at z11 and above. The build's last step flushed the cache, because that is
what it had always done. By 02:12 every edge node was missing every tile above z10, and the queue
passed its limit of 10,000 jobs.

At 02:14 the renderer's autoscaler added nodes, but new render nodes take nine minutes to load the
elevation data, so they arrived long after the damage. At 02:19 the pager went off. The on-call
engineer, Mei, saw a queue of 31,750 and a hit rate of 8%, and could do very little about either:
there was no way to serve the previous tiles, because the flush had removed them.

From 02:30 onward, the queue drained in waves. Each wave looked like a recovery, and each was
followed by another climb as clients retried. Customers saw blank squares for 95 minutes in total,
mostly in Europe, where it was the middle of the night, and in Japan, where it was not.

Three things in this RFC come directly from that night:

1. **No flush.** A build makes a new `dataset_rev`, and the old tiles stay valid until nobody wants them.
2. **Single flight.** The retries were about 80% of the queue. They would have been waiters instead.
3. **Serving the previous revision.** A slightly old contour line beats a blank square every time.

Nobody did anything wrong that night, and the flush had been in the script since 2021. That is
rather the point: the old design needed people to remember something, and this one does not.

## Appendix: questions from the first review

**Does the single-flight guard hold across nodes?** No, only per node. With 37 nodes the worst case
is 37 renders of one tile, which is fine; the guard exists to stop two hundred, not to reach one.

**What stops a client from filling the object store with junk coordinates?** Coordinates outside a
style's zoom and bounds are refused before any cache lookup, and each tile can only exist once.

**Can a customer force a fresh render?** No, and they have never needed to. Support can, through the
purge command, and it leaves an audit line.

**Why five seconds for the poll?** It is fast enough that a publish feels instant to the person doing
it and slow enough that the table stays boring. We tried one second in staging; the only thing that
changed was the database's graph.

**Does this make the renderer's job queue less important?** It makes it less busy. It remains the
thing that falls over last, and its limit stays where it is.

**What happens to tiles when a customer leaves?** Nothing, because tiles are not per customer. Their
overlays are deleted with the contract, and an overlay's tiles are keyed by the overlay's revision,
so they stop being requested and expire on the normal schedule.

## Appendix: glossary of cache terms

Hot set
: The small share of tiles that receive most requests. Ours is about 3% of distinct tiles.

Single flight
: At most one render per missing tile, with everyone else waiting on its result.

Write-through
: Writing to the cache as part of producing a value, rather than on a later read.

Revision
: A counter that names one published version of a style; see [the glossary](glossary-multilingual.md).

## Appendix: worked example

A hiker opens the Skåne coast at z15 on a Saturday morning. The client asks for
`/v2/tiles/outdoor/15/17512/10187.png`. The edge node finds no entry in memory, because this
stretch of coast is not in the hot set, and reads `t/outdoor/48/2026-02-01/15/17512/10187.png` from
the bucket in 22 ms. The node returns the tile, inserts it into memory, and the next hundred people
on that path get it in under a millisecond. Nobody rendered anything, and when the style is
published on Monday the old tile simply stops being asked for.

[^sampling]: One request in fifty, sampled by a hash of the tile coordinates, so a tile's requests are all kept or all dropped.
[^replay]: The replay ran on the January sample against a staging region with the production render fleet's latency distribution, not its real load.
[^keys]: API keys are checked and stripped by the edge before the cache lookup; see [Authentication](api-reference.md#authentication).
