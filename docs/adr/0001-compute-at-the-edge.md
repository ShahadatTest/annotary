# Compute at the edge: the pusher renders and re-anchors, the server only stores and serves

Decided 2026-08-18. Annotary will run as a hosted multi-tenant service in Phase 2, and the owner does not want to pay for CPU that a user's machine can spend instead. So the **client that pushes a Version** (the CLI now; a browser via the same Rust crates compiled to WASM later) does all per-Version computation — hashing, asset scan and dimensions, image derivatives, histogram/char diff and Thread re-anchoring, and **Markdown → HTML rendering** — and submits the results with the commit. The server validates, stores, authorizes, serializes writes and serves; per-*view* cost is a SQLite query plus static content-addressed blobs. A heavier push is accepted because pushes happen inside agent sessions where latency is already dominated by other work, while viewing must feel instant.

Considered and rejected: server-side render cached per Version (cheap, but cost lands on the host and fixes ship as deploys); browser-side WASM render per view (zero host cost, but every view pays and it endangers the < 100 ms first-paint budget).

Consequences: rendered HTML must be **viewer-agnostic** — semantic markup with `data-l` source-line ranges, no CSS/JS/chrome — so web, iOS and Android viewers all consume the same blob and rendering fixes ship as a CLI release rather than an app-store review. Each Version records the renderer version; raw Markdown is always stored, and the server keeps the same crates as a **fallback** renderer (`rerender`, missing/too-old HTML) but never renders by default. Re-anchoring placements are accepted from any Member with `write` on the Vault (they can only affect their own Tenant); the server may spot-verify with the same pure function.
