# Concurrent edits: `push` checks content, not version numbers; merging is done with ordinary tools

Decided 2026-10-07 (ticket 17). Phase 1 assumed one writer per Document at a time: a push whose Sidecar `base_version` was behind the head printed "head moved" on stderr and landed anyway (refused only under `--strict`). With parallel git worktrees (several agents, or an agent and a human, editing one shared Document) that loses work. The second push replaces the first one's edits in the head, Threads anchored on the first one's text orphan, and an agent that ignores stderr never notices. A stale, unedited checkout pushed by mistake silently reverts the head.

**Decision.** When the base is behind the head and the file differs from the head, `push` checks whether the file **already contains the changes the head made since the base**. It fetches the base and head Markdown + manifests and runs `annotary_diff::contains_changes` on the text and `missing_asset_changes` on the manifests (`annotary_store::check_head_changes`). Contained (the Member merged with git, by hand, or any other way) ⇒ a normal push from the head, no warning, re-anchored head → file as always. Not contained ⇒ refused (exit 5, `head_moved`) **before re-anchoring and before uploading anything**, with the missing base→head hunks printed as a unified diff (and as `missing[]` / `assets[]` under `--json`) so the Member or agent can put them in and push again. Annotary never writes a merge into anyone's file and has no merge verb. Humans and agents already know how to merge a Markdown file; Annotary only checks the result.

- **The check** is a line-level 3-way comparison over the histogram line diffs base→head and base→local, grouped into chunks of overlapping changes. A chunk the head changed is contained when local's text for it equals the head's. When both sides inserted at one point, it is contained when the head's insertion is a run inside local's (both appended a section). When both changed it differently, the same comparison is repeated at word-token level (UAX #29, as re-anchoring uses). Two diffs of the same base can place one change differently next to another edit or among repeated lines, so the comparison is repeated under a few valid alignments: histogram / minimal Myers, pure edits slid up / down, a replacement split at the earliest copy of the item that follows it. The change counts as contained when any alignment shows it. Each alignment is sound on its own (local must read exactly like the head in an aligned region), so the retries remove false refusals and never add false acceptances. A heuristic "diff head → local and look for dropped head text" second opinion was tried and rejected: when the head only deleted a line that also occurs elsewhere, it accepted files that lacked the change.
- **Assets**: for every `ref` whose entry differs between the base and head manifests (added, removed, other bytes, present ↔ missing), the pushed manifest must have the head's entry. A `ref` the head did not touch is free to change.
- **Wire**: the commit carries `contains_head: H` (the head the CLI checked) or `discard_head_changes: true`. With `base_version < head` the server accepts `contains_head == head` (and, with `serve --verify-edge on`, the default, re-runs the same check on the three blobs it holds and refuses a mismatch), refuses `contains_head ≠ head` with "head moved again (now vN)", and refuses a commit that claims neither. `discard_head_changes` is accepted, and the `version.pushed` event records `discarded: [versions]` (`wait` prints `discarding vN`).
- **Conflicted Sidecars self-heal.** `Binding` reads a `.annotary` that git left with conflict markers (two-way or diff3) side by side. The two sides must name the same Document and Vault (else exit 5, "keep one side"). `base_version` is the lower of the two (the check then covers more of the head's changes), and `actions.available` is sent only when both sides agree. The next push or pull writes the file clean. Merging a branch only asks the Member to resolve the Markdown.

**Open questions, as decided.**
1. *Overlaps that do not resolve at token level* (local merged the head's sentence and then reworded that same sentence) are **refused**, and the diff shows the head's version. In the git flow such an overlap was a git conflict the Member already resolved, so a second look is cheap, and `--discard-head-changes` exists for "I have accounted for it". The same holds for edits separated only by blank or repeated lines whose alignment no tried diff gets right: refused, the safe direction.
2. *Verify switch*: one switch for everything the edge computes. `serve --verify-placements` (ticket 07) became **`serve --verify-edge on|off`**, with the old name kept as an alias (`Store::verify_edge` / `set_verify_edge`). Off = trust the edge (a hosted server may choose it, ADR 0001).
3. *Retry on "head moved again"*: **no automatic retry** in this ticket. The CLI refuses and asks for a re-run; revisit if it shows up in practice.

**Considered and rejected.**
- *Warn and overwrite* (Phase 1): visible only to readers of stderr, and loses work by default.
- *`pull --merge` writing conflict markers into the `.md`*: Annotary would own merge UX, write into people's files, and need a resolution protocol. Git and editors already do this.
- *Algorithmic auto-merge of concurrent uploads* (the Phase 1 backlog item, now superseded): a server-side merge produces text nobody wrote or reviewed, and it runs on server CPU against ADR 0001.

**Consequences.** An older CLI pushing over a moved head is now refused (409 `head_moved`, with a hint to upgrade or pass `--discard-head-changes`). The server keeps answering everything else from older clients. Some pushes that are semantically fine are refused (the overlap cases above); the diff shows why, and `--discard-head-changes` is the deliberately long escape, visible in stderr and in the event log. `--strict` no longer mentions head moved, because the refusal is the default. Versions stay a single line: a contained push is a normal next Version, and nothing branches.
